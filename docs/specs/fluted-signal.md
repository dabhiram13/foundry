# Fluted Signal public site

## Brief and boundaries

Replace the current neutral landing and documentation controls with a coherent,
distinctive public visual system. Work in the real Astro/React site. This is not
the managed workspace interface, a separate showcase, or evidence that the full
Devin-like product has shipped. Published npm and connected source capabilities
remain clearly distinguished. No provider, account, release or merge is implied.

## Research and direction

- [Cult UI Fluted Glass](https://www.cult-ui.com/docs/components/fluted-glass)
  and its [source registry](https://www.cult-ui.com/r/fluted-glass.json): ribbed
  optical treatment over a local original image, not a stock remote photo.
- [Cult UI Halo Button](https://www.cult-ui.com/docs/components/halo-button)
  and its [source registry](https://www.cult-ui.com/r/halo-button.json): an
  emphasis rim for primary actions only. Preserve native links and buttons;
  do not add staggered letters or a second animation/control framework.
- [shadcn](https://ui.shadcn.com/docs/components/radix/button) remains the base
  action API. Starlight and Pagefind remain the actual docs navigation/search.

Fluted Signal combines an ink-dark landing, editorial typography, a local lilac
and citrus optical object and restrained chrome. Docs retain light/dark/auto
themes with the same semantic tokens. Source availability is not trademark or
exclusivity clearance; no claim that this is the world's best or unknown design.

## Flows, realistic content and component map

1. Understand Foundry and its current limits, then install or read the docs.
2. Inspect the six-step workflow with realistic booking-product examples, not
   a fake live dashboard or fabricated running agents.
3. Check published versus source-preview availability and provider requirements.
4. Use docs search, follow a setup guide and copy a real command.
5. Navigate and switch docs themes on desktop or mobile.

The existing landing, workflow disclosure, native mobile menu, install panel,
clipboard states, availability labels, specialist summaries, FAQ and footer are
all in scope. So are docs search dialog/input/results/empty/loading, clear and
load-more buttons, theme select/options, navigation/disclosures, table overflow,
code-copy controls and pagination. Do not add unrelated forms, sliders or fake
loading/error widgets just to display a component kit.

## Design and implementation criteria

- FS-01: Implement the actual pre-rendered public site with useful navigation,
  accurate product copy, metadata, local identity and working installation links.
- FS-02: Apply one documented semantic color, typography, spacing and control
  system to landing and docs, including docs light/dark themes.
- FS-03: Use source-owned, attributed optical-glass and primary-action patterns.
  Decorative enhancement must not block text, navigation, scroll or first paint.
  Keep a static local fallback if JavaScript, WebGL or hydration is unavailable.
- FS-04: Preserve native semantics, keyboard/focus, at least 44px standalone
  targets, readable contrast, responsive layout and reduced-motion behavior.
- FS-05: Preserve real copy success/failure/retry/unavailable feedback and native
  search/loading/empty results, selection, open and disabled states.
- FS-06: Pass site type/build/tests and applicable tooling, catalog, runtime,
  installed-package and exact-index security gates. Record any unverified visual
  acceptance separately instead of calling static tests rendered evidence.

## Verification and owner acceptance

Compare the actual previous and new pages at desktop/mobile widths. Check the
installation flow, workflow disclosures, menu Escape/focus, FAQ, clipboard
success/denied/unavailable, search query/empty/clear, docs themes, keyboard,
contrast, horizontal overflow, no-JavaScript fallback and reduced motion.
Browser-recorded testing requires explicit approval for this run. Shell checks
alone do not establish appearance, browser behavior or owner acceptance.

No merge or release without separate explicit approval.
