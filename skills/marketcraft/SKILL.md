# Marketcraft

The framework checkout is `{{FRAMEWORK_ROOT}}`. Read its `docs/WORKFLOW.md`,
`docs/WORKFLOW-CONTRACTS.md`, and `docs/PROVIDERS.md`. This checkout supplies the
installer and reusable contracts; build application code in the product workspace.

1. Read the idea/change and workspace instructions. Sri remains the product driver;
   choose the next useful action at small, feature, or product depth. A planning or
   review request authorizes that scope only. Use the guide for a read-only next
   step, not as permission to implement, spend, connect, or publish.
2. Continue in the existing product when requested. For a new product, resolve a
   lowercase folder name from the product name beside this framework by default.
   Follow an already supplied location. Ask only if the target is ambiguous or the
   product name is missing. Tell the owner the selected location in plain language.
   Do not rename this framework checkout or change repository remotes.
3. For authorized installation, run the framework's `scripts/marketcraft.py install`
   with the resolved absolute product folder. If `.foundry/install.json` exists,
   use its installed runtime and resume current work; update only when requested.
   If a proposed new folder contains another project, resolve the target before
   installing. Preserve owner files, stack, checks, and instructions.
4. Installation-only requests end with the setup result. For authorized product
   work, use the installed workflow. Research only decision-changing uncertainty:
   dated evidence and assumptions feed a switching/pricing/channel/unit-economics
   thesis, product brief, and criteria. Competitor offers and synthetic personas
   are not demonstrated customer demand. Reuse valid existing product artifacts.
5. For UI work follow the six UX handoffs at the selected depth. Keep the adopted
   product direction authoritative over generic aesthetic recipes. Configure real
   project checks and use native scoped delegation where available. Reviewers are
   read-only; the coordinator owns integration and final lifecycle transitions.
6. Report the selected product folder, implemented or reviewed outcome, actual
   evidence, and blockers. A separate Codex workspace may require opening that
   folder. Distinguish local verification, deployed verification, and owner
   acceptance. Preserve model/reasoning inheritance and native hook trust review.

Existing authorization remains valid. Missing capabilities never authorize a new
account, paid API, dependency install, subscription change, or publishing action.
If the framework checkout is unavailable, explain how to reconnect its current
location. Do not fetch a substitute framework or change unrelated projects.

Compatibility names remain `product-foundry`, `foundry-*`, `scripts/foundry.py`,
and `.foundry`; use `marketcraft` and `scripts/marketcraft.py` for new instructions.
